\section{Executive Summary}
\begin{pocbox}{Project Research and Audit Repository}

    \url{https://github.com/hyperledger/cacti/tree/main/researches}

    These documents contain the empirical data, bottleneck analysis, and strategic roadmap for the Cacti Cleanup Initiative.

\vspace{0.5cm}

Hyperledger Cacti stands as the definitive enterprise-grade framework for blockchain interoperability. Born from the strategic merger of Hyperledger Cactus and Weaver Lab, it provides a pluggable toolkit to link heterogeneous Distributed Ledger Technologies (DLTs) such as Fabric, Besu, Corda, and Ethereum. While this merger has created an unparalleled feature set—enabling everything from simple ledger state queries to standardized IETF SATP asset transfers—it has also inherited significant "fragmentation debt." This debt manifests as disjointed documentation, architectural silos, and inefficient infrastructure that collectively slow down innovation and discourage new contributors.

The \textbf{Cacti Cleanup Initiative} is a holistic overhauling strategy designed to transform this fragmented landscape into a cohesive, high-performance contributor ecosystem. The initiative focuses on three strategic pillars: \textbf{Documentation Restructuring}, \textbf{Onboarding Excellence}, and \textbf{Infrastructure Optimization}. By reconciling legacy naming conventions, surfacing hidden architectural specs (such as the 50+ Weaver RFCs), and implementing a tiered documentation model (Levels 1, 2, and 3), we will provide users with a clear navigation path aligned with their technical intent. 

Simultaneously, we will slash the "Time-to-First-Run" to 15 minutes through container-first strategies and unified quickstart guides. This project also maintains its commitment to infrastructure hardening, aiming to reduce CI feedback loops from 45 minutes to under 15 minutes via advanced parallelization and cross-job caching. This is not a mere cleanup; it is a technical synthesis intended to build the foundation for Cacti's next phase of growth as the global standard for DLT interoperation.

\begin{tcolorbox}[colback=blue!5!white, colframe=blue!60!black,
  title=Core Project Mandate, fonttitle=\bfseries, arc=4pt]
To deliver a unified, developer-centric ecosystem for Hyperledger Cacti by:
\begin{itemize}[leftmargin=*]
    \item \textbf{Restructuring Documentation:} Transitioning from legacy silos to a unified, immersion-based Tiered Model.
    \item \textbf{Streamlining Onboarding:} Slashing "Time-to-First-Run" to 15 minutes via container-first strategies.
    \item \textbf{Optimizing Infrastructure:} Accelerating CI/CD pipelines by >60\% through persistent caching and parallelization.
    \item \textbf{Cleaning the Codebase:} Resolving namespace debt and retiring deprecated components.
\end{itemize}
\end{tcolorbox}

\section{The Cacti Vision: A Unified Interoperability Fabric}

To overhaul Cacti effectively, one must first understand its unique value proposition. Unlike many "bridge" projects that introduce a central relay chain, Cacti prioritizes \textbf{Self-Sovereignty} and \textbf{Native Consensus}. It allows networks to remain independent while providing trust-minimized paths for interaction.

My research into the project's origins and current state reveals a multi-faceted architecture:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Connector-Driven Connectivity:} Using plugins to abstract the complexity of specific DLT protocols (e.g., the Fabric connector handling MSP IDs and discovery).
    \item \textbf{Orchestration Flexibility:} Offering both a centralized Node Server model (legacy Cactus) for straightforward API-driven workflows and a distributed Relay model (legacy Weaver) for asynchronous, peer-to-peer interoperation.
    \item \textbf{Standards-Based Transfers:} Implementing the IETF SATP protocol to ensure that asset transfers are not just technical successes, but compliant with emerging regulatory standards.
\end{enumerate}

Cacti is effectively the "Internet Protocol (IP) Layer" for blockchains. Our goal in this overhaul is to make this layer as easy to "plug into" as a standard network cable.

\section{The Problem: The High Cost of Fragmentation}

The current state of Hyperledger Cacti presents a paradox: it possesses one of the most comprehensive interoperability feature sets in the industry, yet much of its value is obscured by "merger legacy." 

\subsection{Documentation Fragmentation and the "Discovery Gap"}
Documentation is the primary user interface of an open-source project. Currently, Cacti's documentation is split across multiple directories that still reflect pre-merger identities. Critical architectural specifications, such as the 50+ Weaver RFCs, are "dark matter"—extremely valuable but effectively invisible to the average user because they are buried deep within the \texttt{weaver/} subdirectory without root-level navigation. 

Furthermore, "Link Rot" has set in; numerous files still point to the defunct \texttt{hyperledger/cactus} repository, leading to 404 errors that damage project credibility. This discovery gap forces users to read source code to understand basic protocols, creating a high cognitive load that discourages adoption.

\subsection{Onboarding Friction: The "Heavy" Barrier}
To build Cacti from source, a contributor currently needs JDK, Go, Foundry, Python, and Docker. While these are necessary for the full framework, they represent a massive barrier for someone who just wants to use a "Connector as a Library" (Level 1 immersion). The lack of a unified \texttt{QUICKSTART.md} means new users spend hours troubleshooting environment variables before they ever see an asset move between chains. 

In the demo ecosystem (\texttt{cacti-demos}), instructions are repetitive and setup is manual. The use of unofficial Docker images (e.g., \texttt{aaugusto11/}) in core demos creates security concerns and a sense of "incompleteness" that contradicts Cacti's enterprise-grade mission.

\subsection{Infrastructure Debt: The 45-Minute Feedback Loop}
As detailed in our technical audit, the CI/CD pipeline is currently a bottleneck. A full build taking 45 minutes means a developer can only perform a few iterations per day. This delay is exacerbated by redundant linking of monorepo packages and the lack of artifact persistence across jobs. In a project as large as Cacti, an inefficient CI system is not just an inconvenience; it is a fundamental drag on innovation.

\section{Full Technical Implementation}

\subsection{Infrastructure: The "Fast Feedback" Pipeline}

The core of the infrastructure overhaul is the move from a linear, "monolithic" approach to a decoupled, "fast feedback" pipeline. We will implement three high-impact architectural changes:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Call Chain Decoupling:} We will refactor \texttt{ci.yaml} so that \texttt{packages-workflow} and \texttt{code-quality-checks} run in parallel. Tests will trigger as soon as the base dependency install and build stages finish, rather than waiting for documentation linting or codegen checks to complete.
    \item \textbf{Persistent Monorepo Caching:} We will implement an "Install-Once" strategy using a centralized \texttt{install-dependencies} job. This job will cache the entire \texttt{.yarn/cache} and \texttt{node\_modules} tree. Subsequent jobs will restore this cache in seconds, eliminating 3--5 minutes of setup per job. We will also enable \texttt{.tsbuildinfo} caching to allow for incremental TypeScript compilation across different CI jobs.
    \item \textbf{Build-Once, Run-Many (Artifacts):} For complex sub-systems like Weaver, we will move away from building components from source in every integration test. A single \texttt{weaver-build} job will produce pre-built binaries (Relay, Drivers, CLI), which downstream matrix jobs will download as GitHub Action Artifacts. This reduces the setup time for each of the 12+ Weaver test suites by ~5 minutes.
\end{enumerate}

\subsection{Docker Orchestration: Remote Layer Caching}

To address the 20-minute rebuild times of massive images like \textit{Fabric All-in-One}, we will integrate \texttt{docker/build-push-action@v5} with GitHub Actions' remote cache backends (\texttt{type=gha}). This ensures that base OS layers and static binary downloads are cached across PRs, potentially saving 25+ minutes on image-heavy runs.

\subsection{Documentation Strategy: Tiered Unified Knowledge}

The centerpiece of the documentation overhaul is the transition from a "Project-History" structure to a "User-Intent" structure. We will implement the \textbf{Three Levels of Immersion} throughout the MkDocs site and root README:

\subsubsection{Level 1: Connector as a Library (Low Immersion)}
This tier targets developers who need simple DLT access. 
\begin{itemize}
    \item \textbf{Fabric Missing Link:} We will implement a dedicated Fabric Level 1 tutorial to complement the existing Ethereum one, showing how to use the \texttt{@hyperledger/cactus-plugin-ledger-connector-fabric} package as a standalone dependency.
    \item \textbf{Surrogate READMEs:} Each connector package will have a standardized README template that focuses exclusively on programmatic usage, hiding framework-level complexity.
\end{itemize}

\subsubsection{Level 2: API Server with Plugins (Medium Immersion)}
Targets system integrators building microservices.
\begin{itemize}
    \item \textbf{OpenAPI Visibility:} We will surface the Swagger/OpenAPI endpoints for the Cacti API Server at the root of the doc site.
    \item \textbf{Plugin Catalog:} Create a unified searchable list of all 20+ available plugins with their configuration schemas.
\end{itemize}

\subsubsection{Level 3: Full Framework (High Immersion)}
Targets architects designing complex interoperability workflows.
\begin{itemize}
    \item \textbf{Protocol Unified Guides:} We will unify the documentation for SATP Hermes and Weaver Data Sharing under a single "Enterprise Interoperability" section.
    \item \textbf{The RFC Portal:} The 50+ Weaver RFCs will be indexed in a root-level \texttt{REFERENCES.md} and cross-linked into relevant technical guides to ensure protocol specifications are always "one click away."
\end{itemize}

\subsection{Living Architecture: Architecture-as-Code}
Existing architecture diagrams are static PNG files that are already outdated. I will lead the transition to \textbf{Mermaid.js} integration. 
\begin{itemize}
    \item \textbf{Versioned Visuals:} Diagrams will be stored as \texttt{.mmd} files in the repository.
    \item \textbf{Automated Rendering:} These will be rendered natively by the MkDocs site and GitHub, ensuring that architectural changes in PRs are reflected in the visuals immediately.
\end{itemize}

\subsection{Onboarding: The 15-Minute Contributor Path}
To solve the "Prerequisite Barrier," we will introduce a \textbf{Container-First Onboarding strategy}:
\begin{itemize}[leftmargin=*]
    \item \textbf{QUICKSTART.md:} A single, root-level file that uses Docker Compose to spin up a "Hello World" SATP transfer. This allows new users to see Cacti in action before committing to a full multi-language build environment setup.
    \item \textbf{DECISION\_GUIDE.md:} A visual flowchart helping users choose between the Cactus orchestration path and the Weaver protocol path based on their DLTs and trust assumptions.
    \item \textbf{Standardized Demo Patterns:} I will refactor the 10+ demos in \texttt{cacti-demos/} to use a consistent "Terminal Pattern" (Terminal 1 = Gateway, Terminal 2 = Ledger, etc.) and provide a \texttt{setup.sh} script to eliminate the current "cd ../../../" duplication.
\end{itemize}

\subsection{Documentation as a Community Funnel: The Good First Issue Program}
As synthesized in our cross-repo research (\texttt{some\_example\_repos/cacti\_onboarding\_research/00\_synthesis.md}), the most successful open-source projects (VS Code, Kubernetes, Fabric) use documentation as a primary funnel for new contributors. Cacti currently lacks a visible "on-ramp" for non-code or low-complexity code contributions. 

I will implement a \textbf{Structured Contributor Funnel} by:
\begin{itemize}[leftmargin=*]
    \item \textbf{Curating 20+ Good First Issues:} These will specifically target the Link Rot Audit findings and small documentation gaps identified in Phase 1.
    \item \textbf{The "First PR" Guide:} I will create a dedicated guide (\texttt{docs/contributing/your-first-pr.md}) that uses one of the documentation fixes as a walk-through example, teaching the user the Conventional Commits and DCO signing requirements in a low-stakes environment.
    \item \textbf{Automated Quality Coaching:} I will integrate \texttt{markdownlint} and a link-checker into the CI pipeline. This ensures that new contributors receive immediate, automated feedback on their documentation PRs, reducing the manual review burden on maintainers and coaching the contributor toward Cacti's quality standards.
\end{itemize}

\subsection{Standardizing the Demo Ecosystem: The 'Golden Terminal' Pattern}
Currently, a user evaluating Cacti might try the \texttt{supply-chain} example, which uses a specific Docker-in-Docker setup, and then try the \texttt{satp} gateway demo, which uses a completely different multi-terminal manual setup. This inconsistency is a major "Immersion Barrier."

I will lead the effort to \textbf{Standardize the Demo Experience} using what I call the "Golden Terminal" pattern:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Terminal 1 (The Engine):} Reserved for the Cacti API Server or Weaver Relay.
    \item \textbf{Terminal 2 (The Ledger):} Reserved for the Docker logs of the DLT network.
    \item \textbf{Terminal 3 (The Actor):} Reserved for the interactive scripts or SDK calls.
\end{enumerate}
By refactoring all demo READMEs to follow this exact layout, and providing a unified \texttt{Makefile} at the root of \texttt{cacti-demos/}, we ensure that once a user learns how to run one demo, they have effectively learned how to run them all.

\subsection{Codebase Cleanup: Technical Hygiene}
The overhaul concludes with physical repository cleanup to signal project maturity:
\begin{itemize}[leftmargin=*]
    \item \textbf{Namespace Harmonization:} I will surgically rename the 10+ \texttt{cactus-test-*} packages to \texttt{cacti-test-*} to align with the new project identity.
    \item \textbf{Trust and Security:} I will migrate all demo Docker Compose files to use official \texttt{ghcr.io/hyperledger-cacti/} images, replacing unofficial personal registries (\texttt{aaugusto11/}, \texttt{kubaya/}).
    \item \textbf{Hygiene:} Removal of drafting folders and research notes (e.g., \texttt{HarshitK\_proposal\_drafting/}) to maintain a clean root directory.
\end{itemize}

\subsection{Governance and Knowledge Persistence: Architecture Decision Records}
A project of Cacti's scale cannot be maintained through READMEs alone. The "Knowledge Decay" that followed the Cactus-Weaver merger was partly due to the lack of a formal record for why specific architectural choices were made (e.g., why SATP Hermes uses a specific gRPC bridge over Type 3 APIs).

I will introduce the \textbf{Architecture Decision Record (ADR) Framework}:
\begin{itemize}[leftmargin=*]
    \item \textbf{Cacti ADR-001:} Establishing the Tiered Documentation Standard.
    \item \textbf{Cacti ADR-002:} Standardizing the GHCR naming convention for official images.
    \item \textbf{Cacti ADR-003:} CI/CD Fast-Feedback Strategy and Parallelization model.
\end{itemize}
By codifying the results of the Cacti Cleanup Initiative into versioned ADRs in the \texttt{docs/design/} folder, we ensure that the "Synthesis" achieved during this mentorship remains durable for future generations of maintainers.
